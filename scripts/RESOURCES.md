# Resource id architecture (binary AXML mode)

How attr/resource ids flow from the hand-written sources to what the runtime
reads. There are three id spaces:

| Space | Owner | Example |
|---|---|---|
| `0x01……` | Android framework (public + private), incl. CDROID framework extensions | `android:layout_width` = `0x010100f4` |
| `0x0201xxxx` | widgetEx shared lib (`cdroid.widgetex`, fixed ids) | `layout_constraintLeft_toLeftOf` = `0x0201003a` |
| `0x7f……` | each app pak (aapt2 auto-assigned) | app layouts' own resources |

## Hand-maintained sources

| File | What it is |
|---|---|
| `src/gui/res/values/public-final.xml` | AOSP framework public+private ids (0x01) — pins cdroid.pak's framework arsc |
| `src/gui/res/values/attrs_cdroid.xml` | CDROID's own framework-component attrs (candidate_background…) |
| `src/gui/widgetEx/<comp>/res/values/attrs.xml` | widgetEx attr + declare-styleable declarations (androidx port) |
| `src/gui/widgetEx/<comp>/res/values/public.xml` | **the single source of truth** for that component's stable 0x02 ids |
| `scripts/private-final.xml` | checked-in AOSP private-final (source for regenerating framework_attrids) |
| `scripts/cdroid_attrids.txt` | id list for the attrs in attrs_cdroid.xml (feeds framework styleable gen) |
| `src/gui/res/android.jar` | android-34 framework jar (build input only; never packed into any pak) |

## Generated (do not edit)

| File | Generated by | From |
|---|---|---|
| `scripts/framework_attrids.txt` | `gen_framework_attrids.sh` (manual rerun) | AOSP public-final + private-final |
| `src/gui/widgetEx/widgetex_styleable.{h,cc}` | `gen_styleable.py` (build) | widgetEx attrs.xml + public.xml + framework_attrids |
| `src/gui/widget/framework_styleable.{h,cc}` | `gen_styleable.py` (build) | framework attrs.xml + framework/cdroid attrids |
| `widgetex.pak` / `widgetex.apk` | pakbuilder `_compile_shared_lib` | widgetEx res trees (aapt2 `--package-id 0x02`) |
| `cdroid.pak` | pakbuilder `_compile_sdk_res` | `src/gui/res` (aapt2 `-x`, ids locked by public-final.xml) |
| `<app>.pak` + app `R.h` | pakbuilder `_compile_aapt2` | app res + `-I widgetex.apk` + `-I android.jar` |
| `src/gui/widget/internal_R.h` | `aapt2_gen_rh.py` | cdroid framework apk arsc |

## Flows

```
widgetEx:  attrs.xml + public.xml ──gen_styleable──▶ widgetex_styleable.{h,cc}   (what cdroid.so reads)
           widgetEx res trees ──aapt2 --package-id 0x02──▶ widgetex.pak/apk      (what the runtime resolves against)

app pak:   app res ──aapt2 link -I widgetex.apk -I android.jar──▶ binary AXML
           layout refs via xmlns:app="…/apk/res/cdroid.widgetex" ─▶ 0x02 ids in AXML
           (apk/res-auto does NOT reach -I packages — use the cdroid.widgetex URI)

runtime:   obtainStyledAttributes matches AXML attr ids against styleable IDS[]
           by full resource id — 0x02 styleable == 0x02 AXML id.
```

## Rules / pitfalls

1. **Every attr in a layout/scene needs its namespace prefix under binary AXML.**
   Framework attrs → `android:` (`android:layout_width`), widgetEx attrs →
   `app:` with the `cdroid.widgetex` URI. Bare (unprefixed) attrs silently do
   not resolve — the value stays at its default. Diagnose with
   `d.count(struct.pack('<I', expected_id))` over the binary AXML: 0 = unresolved.
2. **Reference values (`@id/…`, `@xml/…`) must be read with `getResourceId`**,
   not `getString` — binary AXML stores them as TYPE_REFERENCE, which string
   paths render as "".
3. **Anchor attrs (`layout_constraint*_toX`) are `reference|enum`** with
   `<enum name="parent" value="0"/>`: read `getResourceId`, fall back to
   `getInt` for the parent sentinel (androidx ConstraintLayout.java:3311).

## Known caveat: 0x010d id squatting

18 of the 21 attrs in `cdroid_attrids.txt` (from attrs_cdroid.xml) sit on ids
that AOSP's private range already assigns to *different* framework attrs
(e.g. CDROID `candidate_background` = `0x010d0024` = AOSP `checkMarkGravity`).
Both name→id mappings coexist in styleable generation (lookup is by name), and
the colliding AOSP names are only referenced from framework declare-styleables,
so it is latent today — but the two files must NOT be merged, and moving the
CDROID custom attrs to a non-colliding range is the eventual fix.

## Note on intermediate files

There are no per-build generated `.txt` intermediates anymore
(`custom_attrids.txt` was removed in the per-component public.xml migration).
The remaining `.txt` files are checked-in, manually regenerated (rarely) build
inputs, so they live in `scripts/` and stay version-controlled.
